This is a great question because it gets to **use-case granularity**, which is one of the biggest architectural decisions in a Clean Architecture application.

Given everything we've designed, I **would not** name the use case after the DTOs. Instead, I'd name the use case after the **business capability**.

For example, the DTOs

```text
PatientAdministrationDTO
CurrentClinicalSummaryDTO
TreatmentPlanSummaryDTO
```

exist because a clinician wants to **view a patient**.

The use case is therefore **not**

```text
GetCurrentClinicalSummary
```

It is

```text
GetPatientOverview
```

and it returns multiple DTOs.

---

```text
application/

    use_cases/

        get_patient_overview/

            get_patient_overview.py
            get_patient_overview_dtos.py

```

Notice the DTOs belong to the use case.

# Why I prefer this

Suppose your Patient screen contains six cards.

```
Patient
─────────────────────────────

Administration

Clinical Summary

Enrollment

Treatment Plan

Current Alerts

Billing Readiness
```

I would **not** create six separate use cases.

Instead

```
GetPatientOverviewUseCase
```

returns everything needed to render the page.

That reduces database round trips.

# My naming convention

I'd consistently use:

```
GetPatientOverviewUseCase
GetTreatmentPlanUseCase
GetMonitoringSummaryUseCase
GetProviderReviewUseCase
GetBillingPeriodUseCase
GetPatientProgressReportUseCase
```

with corresponding request/result DTOs:

```
GetPatientOverviewRequestDTO
GetPatientOverviewResultDTO

GetTreatmentPlanRequestDTO
GetTreatmentPlanResultDTO
```

This gives you a very clean, scalable convention:

* **Domain** → business entities (`Patient`, `TreatmentPlan`, `OutcomeMeasure`)
* **Application** → business capabilities (`GetPatientOverviewUseCase`)
* **DTOs** → data contracts owned by that capability (`GetPatientOverviewResultDTO`, `PatientAdministrationDTO`, etc.)

I think this organization will scale much better than maintaining a large shared `patient_dtos.py` or `treatment_dtos.py`, because each use case evolves independently and its DTOs stay closely aligned with the data that specific workflow actually needs.
